# BriefOps — от заявки к проверенному ответу

Пет-проект автоматизации для небольшой digital-студии. Объединяет приём неструктурированных обращений, разбор, защиту от повторов, мини-CRM, черновик первого ответа, ручную проверку и контроль SLA.

**Бизнес-проблема:** менеджер переносит сообщения из разных каналов в CRM, повторно создаёт сделки, ищет контакты и бюджет в тексте и забывает ответить вовремя.

**Результат автоматизации:** входящая заявка сохраняется, обрабатывается и превращается в карточку с ответственным и черновиком. Сотрудник проверяет данные и согласует ответ. Каждое действие видно в журнале. Экономия времени и рост конверсии пока не измерялись на реальном бизнесе; такие цифры проекту не приписываются.

## Локальный запуск

Требуется Python 3.11 или новее. Для Neon установите зависимости; npm нужен для проверки neon.ts, но не для запуска Python-сервера.

```powershell
cd "ПУТЬ_К_ПРОЕКТУ"
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -X utf8 app.py
```

Откройте **http://127.0.0.1:8787/**. Можно также использовать `run.ps1`, если локальная политика PowerShell разрешает запуск сценариев. Менять системные политики для проекта не требуется: команда Python работает отдельно.

На первом запуске добавятся семь вымышленных обращений. Приложение явно помечено как демо. При настроенном `DATABASE_URL` изменения сохраняются в Neon Postgres, иначе — в `data/briefops.sqlite3`. Повторный запуск не добавляет образцы заново. Остановка — Ctrl+C в окне запуска; после остановки данные остаются.

Чистая отдельная база без примеров:

```powershell
python -X utf8 app.py --empty --db data/clean.sqlite3 --port 8788
```

## Что реализовано

- Ввод обращения свободным текстом с источником, именем и компанией; HTTP API для внешних источников.
- Извлечение услуги, контакта, бюджета и срочности. Контакт и бюджет берутся из текста, а не выдумываются моделью.
- Два режима разбора: автономные правила и LLM через NVIDIA или OpenRouter. При сбое LLM работает резервный разбор.
- Идемпотентный приём: одинаковые `source + message_id` возвращают прежнюю заявку. Другой текст с тем же ключом даёт HTTP 409.
- Межканальная защита от точных повторов: совпадение текста и идентифицированного клиента не создаёт вторую сделку. Одинаковые анонимные сообщения не удаляются автоматически.
- Похожее обращение с тем же контактом, но другим текстом, сохраняется отдельной сделкой с предупреждением. Новая потребность клиента не теряется.
- Мини-CRM с бюджетом клиента, ответственным и этапами. Демонстрационный каталог услуг: сайт, чат-бот, автоматизация.
- Черновик ответа по данным заявки. Он не обещает неподтверждённые цены и даты; при недостатке данных задаёт вопросы.
- Проверка и редактирование полей и текста человеком. Повторное согласование не создаёт второй исходящий ответ.
- SLA 20 минут: одна задача и событие на просроченную заявку, без повторного спама.
- Надёжная очередь SQLite, повторные попытки с задержкой, лимит три попытки, ручной повтор и восстановление незавершённого запуска после перезапуска.
- Журнал действий, поиск, фильтры, канбан и экспорт CSV с защитой от формул.
- Русский адаптивный интерфейс без внешних шрифтов, трекеров и CDN.

## Демонстрация за 3 минуты

1. На экране «Входящие» откройте «Север Логистик»: услуга, бюджет и контакт извлечены, сделка и черновик готовы. Переключитесь на исходное сообщение и историю.
2. Нажмите «Новая заявка» → «Вставить пример сообщения» → «Принять и обработать». Посмотрите, как появится новая карточка.
3. Нажмите «Проверить поля», исправьте одно поле, сохраните. Отредактируйте текст и согласуйте ответ. На доске «Сделки» карточка перейдёт в «Ответ согласован».
4. В «Автоматизации» запустите «Повтор из другого канала». Повтор появится во входящих, но второй сделки не будет.
5. Запустите «Сбой и восстановление». В истории появится неудачная первая попытка, затем успешная вторая. Очередь и исходная заявка сохранятся.
6. Покажите обращение «Линия» с просроченным SLA и журнал. Повторная проверка SLA не создаст ещё одну такую же задачу.

**Важно для демонстрации:** в исходящих сохраняется согласованный текст. Реальной отправки email/Telegram в проекте нет. Это преднамеренная граница MVP, а не имитация успешной доставки.

## n8n

В `workflows/` находятся два экспорта:

- `intake.json`: защищённый Webhook → сохранение заявки → обработка → проверка точного повтора → HTTP-ответ источнику.
- `sla.json`: Schedule Trigger каждые пять минут → идемпотентная проверка SLA.

Экспорты JSON и их связи проверяются тестом. HTTP-контракт интеграции проверяется интеграционными тестами. **На этом ноутбуке n8n не установлен; импорт и выполнение внутри реального движка n8n пока не проверены.** Бизнес-процесс полностью работает во встроенном Python worker, n8n нужен для подключения внешних источников и расписаний.

Настройка локального n8n:

1. Импортируйте каждый JSON через **Import from File**.
2. Получите токен: `python app.py --print-token`. Не публикуйте его; он хранится в `data/automation-token.txt` и исключён из Git.
3. Создайте в n8n credential **Header Auth**: Name = `Authorization`, Value = `Bearer ВАШ_ТОКЕН`.
4. Выберите credential в Webhook и HTTP Request узлах. В экспорт не включены ни секреты, ни фиктивные ID credentials.
5. URL Python API по умолчанию `http://127.0.0.1:8787`. Для n8n на другом компьютере нужен отдельный защищённый deployment; локальный сервер намеренно слушает только loopback.
6. Включите прослушивание тестового Webhook и передайте `examples/inquiry.json`. Для постоянного использования опубликуйте workflow и используйте production URL, показанный вашей установкой n8n.
7. Источник должен передавать стабильный `message_id`, например ID сообщения Telegram или ID отправки формы.

Проверка API напрямую из PowerShell:

```powershell
$briefToken = Get-Content -Raw data/automation-token.txt
$briefHeaders = @{ Authorization = "Bearer $($briefToken.Trim())"; 'Idempotency-Key' = 'form-demo-001' }
$briefBody = Get-Content -Raw -Encoding utf8 examples/inquiry.json
$briefResult = Invoke-RestMethod http://127.0.0.1:8787/api/automation/intake -Method Post -Headers $briefHeaders -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($briefBody))
$briefResult.lead.id
```

Встроенный worker сам заберёт заявку. Для синхронного шага n8n используется `POST /api/automation/process` с `{ "id": "ID_ЗАЯВКИ" }` и тем же credential. Повторный вызов не создаёт второй сделки.

## LLM: NVIDIA и OpenRouter

Выбрана `nvidia/nemotron-3.5-lightning-30b-a3b` через официальный NVIDIA API. Рассуждения отключены (`enable_thinking: false`), ответ запрашивается в JSON. Живой тест трёх вымышленных русских заявок прошёл: услуга, срочность, бюджет и итоговый статус соответствовали ожиданиям. Задержка 0,9–4 с относится только к этому тесту, не к SLA провайдера.

```powershell
$env:BRIEFOPS_LLM_PROVIDER = 'nvidia'
$env:NVIDIA_API_KEY = 'ВАШ_КЛЮЧ'
$env:NVIDIA_MODEL = 'nvidia/nemotron-3.5-lightning-30b-a3b'
python -X utf8 app.py --llm
```

На этом ноутбуке включение уже сохранено в игнорируемом `data/llm-config.json`, ключ — отдельно в `data/nvidia-api-key.txt`. Обычный запуск использует эту локальную настройку. В архиве и Git этих файлов нет. `python app.py --rules` принудительно отключает обращения к модели. Начальное заполнение примеров не расходует API.

`.env.example` — справочник; `.env.local` и `.env` загружаются сервером через python-dotenv. Альтернатива: `BRIEFOPS_LLM_PROVIDER=openrouter`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, запуск с `--llm`. Живой OpenRouter не проверялся.

LLM определяет услугу, краткое содержание и срочность. Черновик ответа строится шаблоном. Контакт и бюджет извлекаются кодом. При сбое API или некорректной схеме включаются резервные правила и событие в журнале. Модель не вызывает инструменты и не отправляет сообщения. Новые заявки при включённой LLM передаются NVIDIA и могут расходовать доступную квоту.

## Архитектура

```text
Форма / источник → HTTP intake → SQLite: заявка + очередь
                                      ↓
                           worker / n8n process
                                      ↓
                 правила или LLM + валидация полей
                                      ↓
             точный повтор? → журнал, без второй сделки
                                      ↓
                  сделка + задача + черновик (транзакция)
                                      ↓
                    проверка и согласование человеком
                                      ↓
                       outbox: согласованный текст

worker / n8n Schedule → SLA sweep → одна задача ответственному
```

Backend: Python HTTP server, Neon Postgres/psycopg или автономный SQLite/WAL, durable job queue. Frontend: HTML/CSS/JavaScript. Workflow: n8n Webhook, HTTP Request, If, Respond to Webhook, Schedule Trigger. Роли сервиса и интерфейса разделены HTTP API.

Внутри транзакции находятся записи в локальную CRM, задача, черновик и завершение задания. При реальной внешней CRM потребуется outbox для интеграционных событий, внешний idempotency key и подтверждение доставки: транзакцию SQLite нельзя расширить на сторонний сервис.

## Тестирование

```powershell
python -m unittest discover -s tests -v
node --check static/app.js
```

Тесты используют отдельные временные базы внутри `artifacts/tests/`, не изменяют демо-базу и не отправляют сообщения. Проверяют конкурентный приём, конфликт ключа, точные и похожие повторы, неполные данные, бюджет, повтор после сбоя, три неудачи и ручной повтор, восстановление очереди, SLA, согласование, резервный разбор, CSRF/origin, токен API и экспорт workflow.

## Границы и следующий этап

Это демонстрационный MVP с вымышленными данными, собственной мини-CRM и локальным outbox. Email/Telegram/внешняя CRM не подключены, отправка и уведомления наружу отсутствуют. Настройка публичного deployment описана в DEPLOYMENT.md; реальные бизнес-метрики не заявляются.

Для пилота с компанией: выбрать один реальный источник и CRM; настроить доступы и правила обработки данных; внедрить доставку через outbox; добавить пользователей, HTTPS, резервные копии и мониторинг; измерить время до первого ответа и количество ручных действий до/после. Изменения в реальных аккаунтах требуют отдельной настройки и согласования.
